# Контент, блог и SEO

## Как владелец публикует статью

1. Пишет в Google Docs.
2. Экспортирует в `.md` (изображения при необходимости переносит отдельно).
3. Отдаёт файл и картинки Codex или Qoder с просьбой «опубликуй как статью».
4. Агент приводит разметку к стандарту, задаёт slug, дату, category, tags, description, alt и метаданные, размещает в коллекции и проверяет локальную сборку.
5. Владелец просматривает локально. После его команды на отправку изменений в `main` GitHub Pages публикуется автоматически.

Никакой CMS или админки. Публикуются только готовые материалы. Черновики никогда не попадают в публичный репозиторий.

## Модель статьи

Используй Content Collection `blog`, источники `src/content/blog/*.md` и (по необходимости) `*.mdx`. Поля:

- `title`: непустая строка;
- `description`: непустая строка для сниппета, ориентир 120–160 символов (без искусственного обрезания);
- `date`: ISO дата `YYYY-MM-DD`;
- `updated`: ISO дата, необязательно;
- `category`: одна основная рубрика;
- `tags`: массив 0–6 коротких тегов;
- `cover`: необязательный путь/asset с alt-текстом;
- `featured`: необязательный boolean;
- `source`: необязательный URL первоисточника для переноса уже опубликованного материала;
- `preserveText`: по умолчанию false. Только по прямому запросу владельца «без изменений» сохраняет исходные заголовок и тело статьи без автотипографирования. Вёрстка и интерфейс остаются общими; SEO обрабатывается обычным образом.
- slug задаётся безопасным именем файла, латиница/дефисы. Менять URL опубликованной статьи без 301-стратегии запрещено.

Пример только для описания структуры (НЕ публиковать автоматически как реальную статью):

```md
---
title: "Как я проверяю гипотезы продвижения"
description: "Порядок работы с гипотезами и метриками до запуска рекламы."
date: 2026-10-22
category: "Аналитика"
tags: ["маркетинг", "эксперименты"]
---

Текст статьи...
```

Пример выдуман — как шаблон, не для публичного сайта.

## Модель кейса

Collection `projects`, источники `src/content/projects/*.md` / `*.mdx`:

- `title`, `summary`, `date`, `tags`, `role` (по известным данным), `cover?`, `featured?`;
- текстовые разделы в теле markdown: контекст, задача, действия, результат (только подтверждённые факты), выводы;
- не требовать KPI, если их нет или они конфиденциальны;
- не публиковать названия клиентов, финансовые данные, скриншоты ЛК и другую внутреннюю информацию без разрешения.

## Страницы и SEO

- Все тексты автоматически проходят Typograf при рендеринге HTML, включая статьи, кейсы, подписи, alt, доступные названия и текстовые SEO-поля. Вручную расставлять неразрывные пробелы не требуется. Код и технические значения обработка сохраняет.
- Telegram и другие контакты получать из `links` в `src/config/site.ts`. В Markdown использовать `[Написать](contact:telegram)` или `[Почта](contact:email)`; рендеринг подставит общий адрес. При незаданном контакте сборка остановится, а не опубликует нерабочую ссылку. Ссылку на личный GitHub владельца не добавлять.

### Метаданные страницы

- Title и description уникальны на каждой странице. Не генерировать десятки пустых tag-страниц.
- Canonical для каждой индексируемой страницы — `https://agubanovv.ru/` и соответствующий путь от корня; без старого префикса репозитория.
- `lang="ru"`, Open Graph/Twitter метатеги, валидная HTML иерархия.
- Разумная оптимизация картинок (WebP/AVIF где уместно), размеры, lazy loading.
- Ссылки на Telegram и YouTube — обычные ссылки; embed — только по необходимости, с учётом приватности и скорости.

### Подтверждение владения сайтом

Выданные Яндекс.Вебмастером, Search Console и Bing значения лежат в `site.verification` (`src/config/site.ts`) и печатаются один раз в `src/components/SEOHead.astro:14` на всех страницах: `yandex-verification`, `google-site-verification`, `msvalidate.01`. Это публичные токены, а не секреты, но менять их нужно только вместе с перевыпуском в самих сервисах. HTML-файл подтверждения в `public/` не нужен — способ «метатег» выбран владельцем.

### Карта сайта

`@astrojs/sitemap` создаёт `sitemap-index.xml` и `sitemap-0.xml`, а плагин `sitemap-public-alias` в `astro.config.mjs` кладёт в привычный `sitemap.xml` список страниц, а не индекс: в вебмастерских панелях владелец видит сразу все адреса с датами и приоритетами, а не одну ссылку на второй файл. Ссылка в `robots.txt` ведёт на `sitemap.xml`.

`src/utils/sitemapMeta.ts` берёт даты из frontmatter и задаёт один scheme приоритетов:

| Адрес | lastmod | priority |
|---|---|---|
| `/` | самая свежая публикация сайта | 1.0 |
| `/blog/`, `/projects/` | самая свежая запись раздела | 0.9 / 0.8 |
| статья или кейс | своя `updated`, иначе `date` | 0.8 |
| `/blog/tags/…/` | самая свежая статья с тегом | 0.4 |
| прочие страницы | нет | 0.5 |

- Дата только реальная: дата сборки в `lastmod` не подставляется, у пустого раздела записи нет `lastmod`.
- Страниц, которых не существует, в карте нет; закрытые от индексации страницы отфильтрованы (`isHiddenPath` в `astro.config.mjs`).

### robots.txt

Единственный источник — `src/utils/robots.ts`. Из него печатают два маршрута: `/robots.txt` (`src/pages/robots.txt.ts`) и отдельная копия для Яндекса `/robots-yandex.txt` (`src/pages/robots-yandex.txt.ts`). Сам Яндекс читает только корневой файл, копия нужна для ручной проверки и для вебмастера.

- Два блока: `User-agent: *` и `User-agent: Yandex`; в обоих `Allow: /` и `Disallow` закрытых страниц.
- `Clean-param:` присутствует только в блоке Яндекса: параметры через `&`, путь `/`. Три группы — метки рекламных кампаний (`utm_*`, `mtm_*`, `utm_referrer`), клик-идентификаторы сетей (`gclid`, `gbraid`, `wbraid`, `msclkid`, `dclid`, `fbclid`, `twclid`, `vkclid`, `yclid`, `srcclid`, `webguruclid`, `_openstat`) и маркеры пересланных ссылок (`ref`, `source`, `source-sign`, `origin`).
- `Sitemap:` одна строка в конце обоих файлов, абсолютный URL.
- `Host:`, `Crawl-delay:` и `Noindex:` не использовать — в документации Яндекса этих директив нет, Google их игнорирует. Запрет индексации страницы задаётся только мета-тегом.

### Хлебные крошки и разметка материалов

- `src/utils/crumbs.ts` строит цепочку «Главная → раздел → страница» с короткими русскими названиями и из неё же собирает `BreadcrumbList`. Видимые крошки рисует `src/components/Breadcrumbs.astro`: на обычных страницах — внутри `<main>` по ширине контейнера (`src/layouts/BaseLayout.astro:20`), на странице публикации — в начале колонки статьи (`src/layouts/PublicationLayout.astro:36`, `breadcrumbs={false}` в оболочке). Цепочка видна и при прямом открытии вложенного URL.
- Крошек нет на главной, на 404 и на закрытых от индексации страницах. У последнего элемента ссылки нет — так требует схема; раздел остаётся единственной ссылкой кроме главной.
- Статья получает `BlogPosting`, кейс — `Article` (`src/layouts/PublicationLayout.astro:21`): реальные заголовок, описание, дата публикации и обновления (полдень по московскому времени), автор только когда он задан в `site.author`, изображение только когда есть обложка. Никаких вымышленных сущностей.
- `src/components/SEOHead.astro:39` печатает несколько JSON-LD блоков, поэтому `BlogPosting`/`Article` и `BreadcrumbList` сосуществуют на одной странице.
- Страница тега добавляет свой уровень цепочки (`src/pages/blog/tags/[tag].astro:14`).
- На главной `WebSite`, опционально `Person` только с фактами, указанными владельцем.

### Закрытое от индексации

`src/utils/routes.ts` хранит `hiddenPaths` — `/legal/consent/`, `/legal/cookies/`, `/legal/privacy/`. Один список используется в трёх местах: `Disallow` в robots, фильтр sitemap и `noindex, follow` на самих страницах (`noindex` в `src/pages/legal/privacy.astro`, `src/pages/legal/cookies.astro`, `src/pages/legal/consent.astro`). Юридические тексты остаются доступными посетителю и по прямым ссылкам из подвала; закрывать их от людей запрещено.

`scripts/check-dist.mjs` не даёт правилам разъезжаться: проверяет отсутствие закрытых страниц в sitemap, согласованность `noindex`/canonical/крошек, директивы robots, реалистичность `lastmod` и совпадение `BreadcrumbList` с видимой цепочкой.

## Аналитика и согласие

Владелец подтвердил Яндекс.Метрику `113586660`. Clarity удалён из компонента, конфигурации и описаний активной аналитики по отдельной команде владельца.

Метрика, карта кликов и Вебвизор загружаются только после явного согласия посетителя. Прокрутка/продолжение посещения согласием не считаются. До выбора, после отказа, при устаревшем/невалидном согласии и без JS нет кода сервиса и noscript-пикселя. `privacyApproved` в конфиге — разрешение владельца на интеграцию, не согласие посетителя.

Узкая полоса во всю ширину снизу содержит равноценные кнопки «Окей» и «Отказаться», ссылку «Подробнее» на отдельное согласие (из него доступны политики). Названия кнопок в текстах согласия, cookie и политики совпадают с полосой. Из подвала можно повторно открыть выбор. Решение и его версия/время — localStorage, 180 дней; при блокировке хранилища выбор действует только в текущей странице. Отзыв прекращает новые запросы, удаляет доступные записи своего домена и перезагружает страницу. Ранее переданные данные требуют отдельного обращения. Смена версии требует нового согласия; открытые вкладки получают изменение через storage.

Оператор и юридические параметры — `site.legal`, почта — `links.privacyEmail`. Политика данных `/legal/privacy/`, cookie `/legal/cookies/`, отдельное согласие `/legal/consent/`. Не описывать несуществующие формы, заказы, рассылки и базы заявок. Не объявлять аналитические идентификаторы полностью анонимными, не обещать отсутствие технических журналов у GitHub Pages, не заявлять неподтверждённую локализацию всех данных.

JavaScript не запускает счётчик на localhost. Smoke проверяет реальные согласованные ID, отсутствие стороннего удалённого трекера и безусловного пикселя, поведение согласия/отзыва/срока/хранилища. Меры на сайте не подтверждают выполнение всех обязанностей оператора вне сайта; см. [ограничения](../guides/PRIVACY.md).
